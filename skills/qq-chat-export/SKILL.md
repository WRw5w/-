# QQ 聊天记录导出与会话恢复

目标：读取指定会话，交付本地 UTF-8 文本及原始 JSON，记录实际覆盖范围；每次结束都交代进程、配置和临时文件的去向。不要把“有缓存”当作 QQ 卡死的诊断。

## 先辨认环境

1. 读取当前目录适用的 AGENTS.md。查现有部署位置、版本、运行进程、启动时间、父子关系及实际监听端口；优先复用已运行服务，不因发现 NapCat 文件夹就认定已运行。
2. 区分普通 QQ、Windows NapCat Shell、Docker NapCat、AstrBot。QQ 的多个 renderer/GPU 子进程是正常架构，不等于重复登录实例。WebUI 端口不等于 OneBot API 端口；反向 WebSocket 客户端也不是 HTTP 服务。
3. 从现有配置读取接口地址和鉴权信息，仅在内存使用；禁止把 token 打印到终端、拼进可分享链接或写入公开文档。调用 get_login_info / get_version_info 验证实际账号和版本。
4. 群聊用 get_group_list 按名字匹配并确定 group_id，私聊用 get_friend_list 确定 user_id。重名或模糊匹配必须让用户确认候选。不得把机器人专用账号误认为用户个人账号。
5. 没有接口时，先把具体启动方式和恢复方案准备好。切换会让正在使用的 QQ 退出、需要扫码或影响另一台机器时说明影响；已有授权则继续，缺少必要授权才询问。不要自动启动整套 AstrBot 来完成单次导出。

## 启动的事务边界

为每次运行建立仓库外的独立工作目录，保存 run-state.json：运行标识、部署路径、QQ/NapCat 版本、原有进程 PID 与创建时间、本次创建进程、监听端口、修改文件清单及前后 SHA-256、备份路径、导出路径、状态。不得保存 token 或密码。

- 采用操作系统持有的互斥锁或独占文件句柄防止并发启动；不能仅凭锁文件存在就断定仍在运行。进程退出后锁应自动释放。
- 本机 QQ 正在使用同一资料目录时，不启动第二个共享该目录的实例，不对现有 QQ 重复注入。
- 优先使用已验证的部署和官方启动方式。记录版本兼容证据；不要直接复用旧版本 package.json 覆盖新版 QQ。新旧部署交叉引用也应先检查。
- 如必须退出原 QQ，先正常退出并有限等待。窗口关闭可能只是最小化到托盘，必须确认进程确实结束。无法正常退出时停止自动流程；强杀会话需要明确授权。
- 禁止 taskkill /IM QQ.exe /F、按名字结束所有 QQ，或因为某进程占据一个常见端口就强杀它。即使终止本次进程，也要重新核对 PID、创建时间、路径和归属，避免 PID 重用。
- 临时接口仅监听 127.0.0.1，使用随机鉴权；优先独立的导出配置，关闭该临时配置中的自动回复/事件转发，不覆盖原有机器人配置。
- NAPCAT_* 等环境变量仅设置在本次子进程环境，不使用 setx，不写用户或系统环境变量。不持久修改 QQ 安装目录、注册表或自启动项。
- 后台服务用隐藏窗口启动；扫码界面等用户确实需要操作的窗口才显示。
- 启动最多一次，限时检查就绪；失败保留脱敏诊断并执行恢复，不循环拉起、不静默升级或卸载。

## 读取与导出

先核对已安装版本的接口定义。群聊调用 get_group_msg_history，私聊调用 get_friend_msg_history。不要混用 message_id、message_seq 和 QQ 内部 msgId。

1. 先取 20 条，验证账号、目标会话、返回码、消息内容和时间。HTTP 200 本身不代表 OneBot 调用成功。
2. 根据当前版本定义确定分页游标、方向和边界包含关系，再向更早记录逐页读取。一次只发一个请求，默认每页不超过 100 条；不要并发轰炸 QQ。
3. 每页立即写入仓库外的 JSONL 检查点。按账号、会话、稳定消息标识去重，保留精确的大整数标识；没有标识时使用原始消息的规范化哈希并在报告注明。
4. 设置页数/总时长上限，例如 500 页或 10 分钟；这是安全上限而非完整历史的定义。空页、游标不推进、连续重复页、接口错误、QQ 无响应都应停止。超时和服务端临时错误最多退避重试两次，鉴权及参数错误不盲重试。
5. 分页是读取数据，不需要反复调用状态接口。长任务使用可用的 task_watcher 或完成事件报告，不高频轮询，不为一次导出创建 heartbeat。达到上限保存断点并明确“部分导出”，不能宣称完整。
6. 输出 messages.jsonl（原始消息）、聊天记录.txt（北京时间、发送者、文本及非文本占位）、manifest.json（账号/会话、版本、条数、起止时间、停止原因、文件哈希和恢复状态）。如用户要求附件，再单独下载，不能把图片链接当作图片已经保存。
7. 读取成功后验证 JSONL 可解析、消息去重、排序、条数和时间范围一致。空结果不能生成假聊天记录；撤回/过期/未同步消息不可凭空恢复。

聊天漫游不保证接口能取回全部云端历史。客户端能显示和接口能返回应分别验证；必要时由用户在 QQ 中加载目标日期后进行一次有限重试。

## 无论成功失败都要恢复

在 try/finally 或等效结构中执行；用户中断也应进入恢复。突然断电则下次根据 run-state.json 核对状态后恢复，不能直接重跑启动。

1. 关闭本次 API 连接、文件句柄、导出工作进程。复用的常驻 NapCat 不应被关闭。
2. 如创建了临时 NapCat，先正常退出，检查其关联进程和端口是否释放；不能自动扩大为“清理全部 QQ”。进程仍占用文件时不清理目录。
3. 恢复本次修改的配置前，确认当前哈希仍是本次写入后的哈希；若被其他任务改动，保留备份并报告冲突，不能覆盖他人的修改。原文件不存在的，只删除本次新建且内容未变的文件。
4. 仅删除清单中属于本次工作目录的临时文件。Windows 使用 Resolve-Path / GetFullPath 验证绝对路径位于目标目录，拒绝指向外部的 junction/symlink；使用 PowerShell -LiteralPath，不跨 shell 拼接删除命令。
5. QQ 聊天数据库、WAL/SHM、登录态、整个 Tencent Files、既有 NapCat cache/config 都不是可随手清理的垃圾。禁止删除这些内容作为卡死的默认修复。
6. 若原普通 QQ 是为本任务退出且用户要求恢复，在临时实例完全退出后用原始正常入口启动一次；清除本次子进程注入环境，确认未带 NapCat 启动参数。报告启动与响应状态；不能把进程出现视为登录成功。
7. 验证导出文件后保留交付物和脱敏运行清单，释放锁，报告残留项及原因。不能在证据不足时声称“零残留”或“已修复卡死”。

## 发布边界

只把 skill、通用脚本和脱敏文档提交到代码仓库。聊天内容、账号运行配置、二维码、日志、凭据、数据库和备份留在本地，除非用户明确指定私有交付渠道。提交前逐一检查暂存文件，避免 git add . 意外上传运行数据。
